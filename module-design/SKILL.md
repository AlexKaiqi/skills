# 问题拆解与模块设计

目标是让相关逻辑集中，让合作方尽量少知道内部细节。模块数量、目录形式和依赖图是否整齐，都不能单独证明设计合理。

## 从问题建立判断

先结合上下文明确用户要得到的结果、约束和本次交付范围。区分已确认需求、候选解法与待验证假设；保留已确定的要求，不把用户提到的技术或模块名称直接当作结论。已有设计是待检验的方案，不是拆解的起点。

从具体场景找出必须解决的子问题：需要什么输入，作出什么判断，返回什么结果，失败后应留下什么状态。分到问题可以验证、关键规则可以解释即可；不要把流程步骤、数据实体或开发任务直接对应成模块。

区分三个决策：**对外需要什么能力、代码怎样封装责任、实现与运行材料怎样放置。** 前一项为后一项提供依据，但不决定其数量和形式。一项能力可以由几个模块协作完成，一个模块也可以支持多项相关能力。

## 用知识与变化推导边界

识别实现这些问题时必须理解的政策、状态规则、表示方式和外部约束。将共同保护一条规则、必须理解同一份私有知识的逻辑放在一起；通过小而清楚的契约向外提供结果。数据和状态归属用于检查责任是否完整，不用于先画模块地图。

对需要新建或重划的边界，同时考虑留在当前责任内部、合并与独立封装。说明拆开后隐藏了什么、哪些真实变化能被限制在局部，以及增加了哪些接口、协调和一致性成本。若调用者仍要理解对方内部才能完成工作，边界没有达到目的。

只服务一个模块的实现与支撑材料留在该模块内。独立业务责任是否成立，要用上述依据判断；调用者数量不是唯一标准。共享也需要当前真实消费者和稳定语义，不能只凭重复字段或预想用途。

复杂设计或边界有争议时，按需读 [推导与检验方法](references/decomposition.md)。方法来源与取舍见 [研究依据](references/sources.md)。

## 验证并收敛

将候选模块放回原场景，检查正常与关键失败路径是否贯通、重要决定是否有负责人、调用者能否只依赖公开契约。再选择来自需求或现有系统的实际变化，检查修改是否会穿透不相关的内部结构。由此调整拆合，不靠增加转发层掩盖耦合。

决定性技术假设用可取得的资料或最小实验验证；业务取舍依据用户要求。无法确认的部分标明影响及验证办法，不编造规则来填满方案。收到新信息时，先定位它推翻了哪个假设或决定，再修改相关部分。

当问题已覆盖、关键责任清楚、主要协作可解释，且进一步拆分没有可指出的收益时，停止增加结构。不确定但不影响当前方案的细节延后处理，保留可调整空间；不为了未来可能出现的需求提前建公共能力。

## 交付

给出规模适当、可供实现或评审的结论：解决哪些问题、推荐怎样归组及原因、通过什么契约合作、关键场景与变化如何检验，以及剩余取舍。简单决定用几句话即可；有争议的边界才展开比较，不强制表格、目录树或额外文件。

需要安排文件时，按已经确定的责任和项目约束落位，分别说明代码归属与运行数据位置。只评审时交付发现与建议；修改设计时同步受影响的说明，不超出本次范围扩展实现。

[声明检查器](references/checker.md) 只在需要时辅助核对已形成的设计，不能发现业务问题或证明边界合理。可参考一个精简的 [推导示例](references/examples.md) 理解方法；不要套用其中的模块结论。
