# 检查器契约与用法

这是完成问题拆解与候选模块设计后的可选辅助。它不会从需求发现子问题，也不会自动推导模块；不要把填写本契约当成开始设计的第一步。

只需要 Python 3.10+ 标准库，无须安装包。脚本是技能内部工具，唯一入口为 `scripts/check_design.py`；不是独立业务模块。目标项目持有自己的设计声明，本技能不硬编码目标项目的模块。

## 在目录尚未创建时使用

从目标仓库运行，将 `<skill-dir>` 替换为本技能实际位置：

```sh
python3 <skill-dir>/scripts/check_design.py --root . --design docs/module-design.json
```

示例假定项目已有 `docs/`，实际使用时替换为项目现有设计位置。不传此参数的兼容默认值是 `architecture/module-design.json`，它不是目录规范，不应据此创建新目录。默认生成 `.reports/module-design.md`。`--check-only` 显示发现而不写报告；`--output -` 输出完整报告；`--check-paths` 额外核对已经存在的路径。设计错误也会生成报告。

退出码：`0` 无机械错误（可能仍有必须评审的警告），`1` 已识别的设计声明问题，`2` 输入或文件操作失败。退出码不是领域设计是否通过的结论。

## 声明结构

以 JSON 避免额外依赖。示例刻意含有一项应报错的设计：优惠策略只供订单使用，却放在外部。

```json
{
  "version": 1,
  "modules": {
    "orders": {
      "path": "orders",
      "purpose": "接受订单并决定是否可以确认",
      "entrypoint": true,
      "owns": ["orders.accepted-order"],
      "decides": ["orders.confirmation"],
      "depends_on": [
        {"module": "stock", "contract": "预留指定数量，返回预留凭据或库存不足"}
      ]
    },
    "stock": {
      "path": "stock",
      "purpose": "保护可售库存与预留生命周期",
      "owns": ["stock.available-quantity"],
      "decides": ["stock.reservation"],
      "independent_reason": "库存独立处理盘点与并发预留，不能由订单直接改变可售数",
      "depends_on": []
    }
  },
  "resources": {
    "discount-policy": {
      "path": "shared/discount-policy.py",
      "owner": "orders",
      "consumers": ["orders"]
    }
  }
}
```

将示例资源移到 `orders/discount-policy.py` 可消除单消费者外置错误；`stock` 单调用者仍有人工评审提示，独立理由不会自动使它通过。

| 字段 | 含义 |
| --- | --- |
| `modules` | 本次评审的业务责任边界，以 ID 为键。不是每个含文件目录都填一项 |
| `path` | 计划存放位置，规范的仓库相对路径。无须已经存在 |
| `purpose` | 向谁提供什么能力及可观察结果，不能只列数据名称 |
| `owns` | 权威事实的稳定 ID；同一事实用同一个 ID，以便检测重复所有权。观测、缓存和派生视图应显式区分，并在设计正文写清来源 |
| `decides` | 模块负责的规则/决定 ID；在设计正文定义含义和验收结果 |
| `depends_on` | 当前真实依赖，每项含提供者 `module` 与公开 `contract`；只声明直接使用，不补传递边 |
| `entrypoint` | 可选，模块确实接受边界外发起的业务操作时为 true；不能为了逃过无消费者提示而设置 |
| `independent_reason` | 可选，暂时只有一个调用者时保留独立业务边界的证据，仍需评审 |
| `resources` | 要核对归属的实现与支撑材料，如配置、类型、适配器、规则实现、文档、夹具、测试，以 ID 为键 |
| `owner` | 该材料的责任模块 ID；只有真正的共享机制候选使用 null |
| `consumers` | 实际需要该材料的业务模块 ID。按责任边界去重，不计文档引用、测试目录、薄装配入口或同模块的多个用例 |
| `shared_reason`, `maintainer` | owner=null 且多业务消费者时必须说明共同语义、共享理由和维护责任；文字非空不能证明合理 |
| `note` | 可选，在顶层记录该声明的范围或尚未验证的状态 |

先从能力推导模块，再用 `owns` 和 `decides` 核对完整性；事实 ID 不对应代码目录或数据库表。领域事实和决策不要误当作应移入调用者的 helper。公开契约若由提供方实现和消费方使用，应声明真实使用的双方；提供方拥有该契约，保留在提供方内部。不可把不使用某材料的模块添加为消费者来规避检查。

跨多个模块的总体设计说明可以不列入业务资源；仅服务一个模块的专项文档应列入该模块。运行数据目录、薄装配、生成产物和仓库工具不充当产品模块。`path` 使用模块的实际或计划路径；`resources` 核对的是源码与支撑材料，不应把 `.data/app.sqlite3` 等生成数据声明为外置私有代码。未声明材料不会被工具自动发现，应在评审时查看文件/方案覆盖情况。

## 能检测什么

- 单消费者材料放在消费模块之外，或归属声明冲突。
- 模块拥有的材料放在自己之外；跨模块消费没有声明公开契约。
- 多消费者共享候选缺少依据或维护责任。
- 同一事实/决定 ID 被多个模块声明为权威、依赖契约空白、自依赖与循环。
- 单调用者模块、没有消费者、没有事实/决定、共享候选，给出人工评审提示。
- 格式、未知字段、重复键/路径/边、未知引用、非法路径；可选的实际路径核对。

无法检测同义但不同 ID 的重复规则、遗漏的规则、虚假消费者、契约语义错误或真实源码穿透。即使声明完整无环，也要用场景和变更推演检查边界。警告不是可以忽略的“低风险”，错误也不应仅靠修改声明掩盖。
