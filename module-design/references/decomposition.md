# 推导与检验方法

用于需求较大或边界有争议时补足判断。可以往返修正，不要求逐项生成文档。

## 1. 把目标展开到可判断的问题

从参与者、使用情境与期望结果开始。先说明什么行为算成功，哪些失败会改变接受、继续或终止的决定，再找完成这些结果必须解决的问题。只保留对当前任务有影响的约束和未知项。

子问题应当能说明输入、必要判断和可观察结果。若只能说“管理某对象”或“完成某一层”，还没有分清要解决什么；若下一步只是已明确责任内部的实现细节，就不必继续作架构拆解。用完整场景检查遗漏，用决定权检查重复承担。

需求给出某个方案时，先判断其必要前提是否成立，以及现有能力或更简单的实现能否满足同一目标。不要在未经验证的解决方向上继续细分模块，也不要以减少需求冒充简化方案。

## 2. 找共同知识，再聚合责任

对关键判断追问：实现者必须知道哪些政策、状态变化、算法或外部语义？哪些细节应由一个地方理解，合作方只需取得结果？先比较这些知识依赖，再命名候选模块。

支持聚合的证据包括：共同保护不可分的规则、共同解释一个状态生命周期、同一项已知政策变化反复要求双方一起修改。共享标识、读取同一份公开事实或经过同一业务流程，不足以证明必须合并。

支持分开的证据包括：内部规则有独立变化原因，交接结果能够清楚描述，调用者无须知道对方的私有表示或执行步骤。独立使用、维护或运行约束可加强这一判断，但不自动要求独立服务。

能力、实体和模块之间没有固定对应关系。先形成能履行承诺的责任组合，再核对其中的数据与决定是否有人维护；不要先按实体分配“所有者”，然后为了证明分配合理而补造职责。

## 3. 比较边界带来的净收益

对新增或争议边界，以现有安排或最简单的可行安排为基线。在相同目标和约束下比较：

- **保留在内部会有什么具体问题？** 若只有命名、文件数量或预想复用，独立边界的必要性仍未成立。
- **独立后调用者可以少知道什么？** 若只是把内部字段和步骤搬到接口上，知识依赖仍然存在。
- **什么变化能被隔离，代价是什么？** 同时计算接口、版本协调、失败恢复与跨边界一致性成本。
- **合并会不会引入无关知识？** 不能为减少依赖数，让每个小改动都必须理解整个系统。

比较聚焦真实争议，不强求固定数量的方案。明确推荐与接受的代价；若缺少决定性证据，给出最小验证及不同结果对边界的影响。未来变化必须有需求或现有差异支持，不能凭想象为抽象寻找用途。

模块内构件也可有清楚职责，不必都提升为平级模块。只服务一个模块的实现、规则与材料应随它维护；有多个消费者时，先判断是否是在消费某个领域的公开能力，再考虑共享机制。

## 4. 把边界放回场景

沿原场景交接输入与结果，明确谁接受或拒绝、谁维护状态、失败由谁解释。接口应提供完整承诺，不能要求调用者自己拼装内部步骤才能保持关键规则。

检查调用者是否在复制对方的判断，是否需要读取私有数据才能继续，以及失败后是否出现无人负责的状态。若有，回到责任聚合；增加接口、事件或协调者本身不能解决归属问题。

用一项有依据的变化检验方案：内部规则改变时，哪些地方必须改、哪些地方只使用不变的公开承诺？公开需求改变时，多方修改可以合理；因泄露实现细节而扩散的修改才是需要修正的耦合。

## 5. 决定何时结束设计

达到当前交付所需的清晰度即可：问题得到覆盖，关键规则有负责人，主要协作及失败结果可解释，关键拆合有依据。此时继续增加结构若没有具体收益，应当停止。

影响关键承诺的未知项需要验证或澄清；不影响当前决定的内部细节留到实现时处理。证据不足时优先选择保持规则完整、以后容易调整的安排，而非同时实现多种假设。

文件布局、存储位置和部署方式按已经形成的责任与项目约束决定；它们不反过来证明业务边界。交付只保留能解释决定、指导实现或支持后续复核的内容，不以文档数量衡量完整性。
